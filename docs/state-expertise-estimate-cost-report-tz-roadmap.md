# ТЗ и roadmap: отчет государственной экспертизы по проверке достоверности определения сметной стоимости

Дата фиксации: `2026-05-28`

## 1. Назначение документа

Документ описывает новый сценарий EvidenceXAI:

- тип отчета: `Отчет государственной экспертизы в части проверки достоверности определения сметной стоимости`;
- пользователь: проектировочная компания, сметный отдел, ГИП, внутренний эксперт;
- вход: папка или комплект документов, уже загруженный и успешно обработанный на вкладке `Документы`;
- выход: интерактивный отчет машинной проверки с этапами, замечаниями, действиями пользователя, XAI-объяснениями и ссылками на источник.

Этот документ является отдельным прикладным ТЗ. Общий roadmap направления государственной экспертизы находится в [state-expertise-roadmap.md](state-expertise-roadmap.md).

## 2. Важное нормативное уточнение

`145` в текущем сценарии — это не ГОСТ, а `Постановление Правительства РФ от 05.03.2007 N 145`.

В интерфейсе и документации нельзя писать `ГОСТ 145`. Правильные формулировки:

- `ПП РФ N 145`;
- `Постановление Правительства РФ N 145`;
- `проверка комплектности по процедурному профилю ПП РФ N 145`;
- `комплектность документов для государственной экспертизы / проверки достоверности определения сметной стоимости`.

Рабочая ссылка на справочный текст: https://www.consultant.ru/document/cons_doc_LAW_66669/

Для production-версии rules pack должен иметь дату актуализации и внутреннюю нормативную проверку, потому что состав документов и процедурные требования могут меняться.

## 3. Цель функции

Добавить в EvidenceXAI специализированный отчет, который помогает проектной организации до подачи документов:

- проверить, соответствует ли название файла его фактическому содержанию;
- проверить комплектность пакета документов для сценария проверки достоверности сметной стоимости;
- проверить качество документов, признаки подписей/печатей и орфографию;
- получить список ошибок и вариантов действий по каждому файлу;
- увидеть, почему система сделала вывод, через XAI;
- заменить проблемный файл и автоматически прогнать замену до текущего этапа;
- получить финальный статус готовности пакета.

## 4. Пользовательский сценарий

1. Пользователь входит в EvidenceXAI.
2. Пользователь выбирает организацию на вкладке `Организации`.
3. Пользователь переходит на вкладку `Документы`.
4. Пользователь загружает папку с комплектом документов.
5. Пользователь нажимает `Обработать ветку`.
6. Документы проходят OCR/text extraction/chunking/indexing.
7. Пользователь переходит на вкладку `Отчеты`.
8. Пользователь выбирает тип отчета `Отчет государственной экспертизы в части проверки достоверности определения сметной стоимости`.
9. Пользователь выбирает папку документов, которые уже успешно прошли обработку на вкладке `Документы`.
10. Пользователь нажимает `Создать и анализировать`.
11. Открывается интерактивная строка проверки из `5` этапов.
12. Система проходит этапы последовательно.
13. Если на этапе найдена ошибка по файлу, пользователь выбирает действие:
    - `Пропустить файл`;
    - `Одобрить файл`;
    - `Загрузить замену`.
14. При загрузке замены новый файл автоматически проходит pipeline до текущего этапа.
15. После устранения блокирующих ошибок система переходит к следующему этапу.
16. На финальном этапе готовность становится `100%`.
17. Пользователь открывает XAI по каждому выводу двойным кликом.
18. Пользователь экспортирует результат проверки.

## 5. Новый тип отчета

В UI вкладки `Отчеты` добавить новый option:

`Отчет государственной экспертизы в части проверки достоверности определения сметной стоимости`

В backend желательно хранить как enum/string:

`state_expertise_estimate_cost_verification`

Совместимость:

- существующие типы отчетов не ломать;
- текущие API routes можно оставить прежними;
- новый тип отчета должен включать специализированный workflow только при выборе этого report_type.

## 6. Выбор папки документов на вкладке `Отчеты`

На вкладке `Отчеты` уже появляется дерево/список обработанных папок. Для нового отчета нужно усилить UX:

- показывать только папки, где все или часть документов имеют статус `processed` или `requires_review`;
- рядом с папкой показывать:
  - количество файлов всего;
  - количество успешно обработанных;
  - количество файлов с ошибкой обработки;
  - дату последней загрузки;
  - среднюю готовность документов;
- если в папке есть необработанные файлы, показывать предупреждение;
- кнопка `Создать и анализировать` для нового типа отчета запускает не обычный report pipeline, а `estimate_cost_expertise_pipeline`.

## 7. Интерактивная строка этапов

### 7.1. Общая идея

После запуска отчета пользователь видит горизонтальную интерактивную строку.

Визуально:

- длинная пустая progress-line;
- линия постепенно заполняется слева направо;
- линия огибает или проходит через круглые stage-nodes;
- каждый stage-node содержит номер и краткое название этапа;
- активный этап подсвечен;
- завершенный этап отмечен галочкой;
- этап с ошибками подсвечен warning/danger;
- справа показывается оценка времени до окончания машинной проверки.

### 7.2. Этапы

1. `Запуск`
2. `Проверка соответствия содержания названию`
3. `Проверка комплектности документов`
4. `Лексическая, орфографическая и визуальная проверка`
5. `Финальная готовность`

### 7.3. ETA справа

Показывать:

- `Осталось примерно: 02:40`;
- `Файлов проверено: 12/48`;
- `Текущий этап: Проверка комплектности`;
- `Ошибок требует решения: 3`.

Первую версию ETA можно считать эвристически:

- базовое время на файл;
- коэффициент по типу файла;
- коэффициент по OCR/vision;
- коэффициент по количеству страниц;
- фактическое среднее время уже обработанных файлов.

## 8. Этап 1. Запуск

### Назначение

Подготовить отчетную задачу и проверить, что выбранная папка пригодна для машинной проверки.

### Проверки

- папка выбрана;
- в папке есть файлы;
- файлы принадлежат выбранной организации;
- файлы имеют допустимые типы;
- документы уже прошли базовую обработку на вкладке `Документы`;
- если часть документов не обработана, вывести предупреждение.

### Выход этапа

- создана workflow-задача;
- сформирован список файлов проверки;
- рассчитан предварительный ETA;
- подготовлен stage state.

### XAI

Для этапа `Запуск` XAI должен объяснять:

- почему выбранный файл включен в проверку;
- почему файл исключен;
- какой статус обработки учитывался;
- почему папка считается пригодной или непригодной.

## 9. Этап 2. Проверка соответствия содержания названию

### Назначение

Проверить, насколько название файла соответствует содержанию внутри файла.

### Примеры

- файл называется `Локальная смета`, а внутри найден `Сводный сметный расчет`;
- файл называется `Пояснительная записка`, а внутри ведомость объемов работ;
- файл называется `Коммерческие предложения`, а внутри только титульный лист;
- файл называется `Раздел 11`, а внутри документ другого раздела.

### Метод проверки

Комбинированный подход:

- извлечь `file_name`;
- нормализовать название:
  - убрать номер версии;
  - убрать дату;
  - убрать технический префикс;
  - распознать ключевые слова;
- извлечь первые страницы/заголовки/титульные блоки;
- классифицировать фактический тип документа;
- сравнить expected type из имени с detected type из содержания;
- посчитать confidence;
- сформировать finding.

Текущая реализация Фазы 2:

- backend использует гибридный классификатор `rules + optional LLM`;
- если локальная LLM доступна через provider abstraction, она возвращает label/confidence/reason в JSON;
- если LLM недоступна, система работает детерминированно через rules scoring;
- XAI по finding сохраняет:
  - метод классификации;
  - тип документа по имени;
  - тип документа по извлеченному тексту;
  - confidence;
  - найденные маркеры;
  - evidence snippets из текста документа;
  - пояснение, почему найдено расхождение.

### Возможные статусы файла

- `match` — название соответствует содержанию;
- `weak_match` — есть частичное совпадение, нужна проверка;
- `mismatch` — название не соответствует содержанию;
- `unknown` — система не смогла уверенно определить тип документа.

### Действия пользователя при ошибке

Для каждого файла с `weak_match`, `mismatch` или `unknown`:

- `Пропустить файл`:
  - файл исключается из дальнейшей проверки;
  - в XAI фиксируется user decision;
  - в итоговом отчете файл помечается как пропущенный пользователем.
- `Одобрить файл`:
  - пользователь подтверждает, что файл можно использовать несмотря на предупреждение;
  - файл идет дальше;
  - XAI фиксирует override.
- `Загрузить замену`:
  - пользователь загружает новый файл;
  - новый файл проходит document pipeline;
  - рядом с файлом появляется отдельная строка прогресса;
  - после достижения текущего этапа система повторяет проверку соответствия.

### XAI по этапу

Двойной клик по выводу открывает объяснение:

- имя файла;
- нормализованное имя;
- обнаруженный тип документа;
- ключевые фразы из содержания;
- найденные страницы/фрагменты;
- confidence;
- почему статус `match/weak_match/mismatch/unknown`;
- какие альтернативные типы рассматривались;
- что пользователь выбрал.

## 10. Этап 3. Проверка комплектности документов

### Назначение

Проверить, хватает ли в выбранной папке документов для сценария:

`государственная экспертиза в части проверки достоверности определения сметной стоимости`.

### Нормативная база

Базовая процедурная рамка:

- `ПП РФ N 145`;
- выбранный профиль подачи;
- тип объекта;
- стадия и состав комплекта;
- внутренний `rules pack` EvidenceXAI.

Важно: точный перечень документов для production должен быть оформлен как версионированный registry и пройти внутреннюю нормативную проверку по актуальной редакции источников.

### Первичный checklist для MVP

Начальный rules pack должен уметь искать и классифицировать такие группы документов:

- заявление/сопроводительные данные подачи, если они входят в выбранный профиль;
- проектная документация или ее релевантные разделы;
- сметная документация:
  - локальные сметные расчеты;
  - объектные сметы;
  - сводный сметный расчет;
  - сметные расчеты на отдельные виды работ;
  - ведомости объемов работ;
  - пояснительная записка к сметной документации;
- документы-обоснования стоимости:
  - прайс-листы;
  - коммерческие предложения;
  - расчеты стоимости оборудования;
  - индексы/нормативы/обоснования пересчета;
- задание на проектирование, если требуется профилем;
- исходно-разрешительная документация, если требуется профилем;
- результаты инженерных изысканий, если связаны с выбранным объектом и составом подачи;
- документы о заявителе/застройщике/техническом заказчике/проектной организации, если они нужны для подачи;
- доверенности/полномочия, если они входят в процедурный профиль;
- дополнительные приложения, заданные пользователем или profile registry.

### Метод проверки

- построить список expected document groups по выбранному profile;
- классифицировать документы из папки;
- сопоставить detected documents с expected groups;
- найти missing/duplicate/ambiguous documents;
- для каждого item сформировать confidence и evidence;
- при неоднозначности запросить решение пользователя.

### Текущая реализация Фазы 2

В backend добавлен расширенный rules pack `Completeness rules pack v3`:

- группы делятся на `mandatory`, `recommended`, `conditional`;
- `mandatory` формирует `danger`, если документ не найден;
- `recommended` формирует `warning`, если документ повышает полноту сметного комплекта, но требует проверки контекста;
- `conditional` формирует `info`, потому что применимость зависит от объекта, финансирования, роли заявителя, наличия инженерных изысканий, СРО, ОКН, экологических требований и других оснований;
- поиск идет по имени файла, исходному имени, относительному пути и извлеченному тексту;
- XAI по каждому missing item сохраняет статус группы, нормативную привязку, проверенные маркеры имени, проверенные маркеры текста и число проверенных документов.

Ограничение: rules pack является инженерным профилем предварительной проверки и должен пройти внутреннюю нормативную проверку перед production-пилотом.

### Возможные статусы checklist item

- `found` — документ найден;
- `missing` — документ не найден;
- `ambiguous` — найдено несколько кандидатов или слабое совпадение;
- `not_required` — не требуется для текущего профиля;
- `user_approved` — подтвержден пользователем;
- `skipped` — исключен пользователем.

### Действия пользователя

Такие же, как на этапе 2:

- `Пропустить файл`;
- `Одобрить файл`;
- `Загрузить замену`.

Дополнительно для missing checklist item:

- `Отметить как не требуется`;
- `Загрузить недостающий документ`;
- `Связать с существующим файлом`.

### XAI по этапу

Двойной клик по выводу открывает:

- ожидаемый тип документа;
- нормативное основание;
- профиль применимости;
- найденные кандидаты;
- почему выбран именно этот файл;
- почему документ считается отсутствующим;
- confidence;
- действие пользователя;
- ссылка на фрагмент/страницу/название файла.

## 11. Этап 4. Лексическая, орфографическая и визуальная проверка

### Назначение

Проверить качество документов перед подачей.

### Подпроверки

1. `Качество документов`
   - есть ли текстовый слой;
   - качество OCR;
   - читаемость;
   - подозрение на пустые страницы;
   - низкое разрешение;
   - поврежденные файлы;
   - неполные страницы.

2. `Печати и подписи`
   - наличие визуального признака подписи;
   - наличие печати/штампа, если применимо;
   - заполненность подписных блоков;
   - дата подписания;
   - ФИО/инициалы;
   - роль подписанта.

3. `Орфография`
   - орфографические ошибки;
   - OCR-ошибки, похожие на орфографию;
   - повторяющиеся пробелы;
   - неправильная пунктуация;
   - подозрительные сокращения;
   - терминологические несоответствия.

### Метод проверки

- text extraction + OCR;
- spell checker;
- domain dictionary для сметной документации;
- whitelist сокращений;
- layout/vision detector для подписей и печатей;
- rules по качеству изображения;
- confidence decomposition.

### Текущая реализация Фазы 2

В backend добавлен `Quality baseline v7`:

- если документ обработан, но текстовый слой пустой, создается warning о необходимости OCR/vision проверки;
- для PDF/изображений считается плотность распознанного текста на страницу;
- если плотность ниже baseline-порога, создается warning о scan-like документе или слабом OCR/text layer;
- орфографический baseline заменен на локальный `local-terminology-rules-v1`: типовые ошибки, проектно-сметная терминология, white-list сокращений и OCR mixed-script noise;
- подписи/печати проверяются по текстовым маркерам: `подпись`, `печать`, `М.П.`, `ГИП`, `утверждаю`, `директор`;
- для изображений и первой страницы PDF работает `layout-baseline-v1`, который ищет signature-like и seal-like компоненты в нижней части страницы;
- для изображений и первой страницы PDF работает `layout-quality-baseline-v1`, который локально оценивает разрешение, контраст, резкость, dark/bright ratio и blank-like признаки;
- XAI сохраняет тип найденного визуального признака, confidence, нормализованный bbox и краткое evidence-описание компонента;
- XAI по визуальному качеству сохраняет измеримые показатели изображения и объясняет, почему скан требует ручной проверки или замены;
- если маркеры не найдены, создается `info`-finding о необходимости layout-aware vision detector;
- если маркеры найдены, создается `info`-finding, что найден только текстовый признак, а не визуально доказанная подпись/печать.

Ограничение: текущая версия не подтверждает юридическую подлинность подписи/печати. Это локальный layout-aware baseline detector, который готовит данные и UX для более сильной vision-модели внутри нашего серверного контура.

### Действия пользователя

Для каждого замечания:

- `Пропустить файл`;
- `Одобрить файл`;
- `Загрузить замену`;
- для орфографии дополнительно:
  - `Игнорировать слово`;
  - `Добавить в словарь организации`;
  - `Создать задачу на исправление`.

### XAI по этапу

Двойной клик открывает:

- найденную ошибку;
- фрагмент текста;
- страницу/координаты;
- тип ошибки;
- словарное или нормативное основание;
- вероятность OCR-noise;
- рекомендацию;
- почему система считает это ошибкой.

## 12. Этап 5. Финальная готовность

### Назначение

Закрыть workflow и показать итоговый статус.

### Поведение

- progress-line заполняется до `100%`;
- все этапы получают статус;
- если блокирующих ошибок нет, отчет получает статус `Готов к проверке экспертом`;
- если ошибки остались, отчет получает статус `Требует решения`;
- пользователь может экспортировать результат.

### Финальный результат

Пользователь получает:

- список файлов;
- статус каждого файла;
- список ошибок;
- список user decisions;
- матрицу комплектности;
- проверку названия/содержания;
- лексические и орфографические замечания;
- замечания по печатям/подписям;
- XAI по каждому выводу;
- итоговую готовность;
- рекомендации;
- экспорт `DOCX/XLSX/HTML/ZIP`.

### Текущая реализация экспорта

Экспорт спецworkflow реализован через существующие API:

- `POST /api/reports/{id}/export/docx`;
- `POST /api/reports/{id}/export/matrix`;
- `POST /api/reports/{id}/export/explanations`;
- `POST /api/reports/{id}/export/package`.

Для отчета типа `state_expertise_estimate_cost_verification` эти endpoints формируют не обычный отчет по требованиям, а специализированные артефакты:

- `DOCX` — summary workflow, этапы, findings, рекомендации, нормативные привязки, решения пользователя и XAI-цепочки;
- `XLSX` — листы `Summary`, `Stages`, `Findings`;
- `XAI HTML` — карточки findings с XAI-цепочками, confidence, источником и рекомендацией;
- `ZIP` — `summary.docx`, `findings.xlsx`, `xai.html`, `workflow.json` и исходные документы выбранного пакета.

В frontend меню `Скачать` показывает специализированные подписи для этого типа отчета: `Summary спецпроверки`, `Матрица findings`, `Workflow + доказательства`, `XAI по каждому выводу`.

### Текущая реализация replacement re-check

Загрузка замены больше не считается мгновенно успешной:

- endpoint `POST /api/estimate-expertise/findings/{id}/replacement` создает replacement-документ и фиксирует решение `replacement_processing`;
- Celery-задача `estimate_expertise_replacement_recheck` обрабатывает replacement-документ через обычный document pipeline;
- после обработки replacement-документ добавляется в `selected_document_ids` отчета;
- исходный finding получает `replacement_resolved`, `replacement_file_name`, `replacement_progress = 100`;
- frontend после загрузки несколько раз опрашивает backend state, чтобы получить фактический результат повторной проверки.

Если replacement-файл сам не проходит текущий этап, backend закрывает исходный finding как замененный и создает новый finding с префиксом `После замены:` и XAI-пояснением `backend re-check replacement-файла`.

### Текущая реализация audit trail

Решения пользователя по findings пишутся в общий журнал аудита организации:

- `estimate_expertise_finding_approved`;
- `estimate_expertise_finding_skipped`;
- `estimate_expertise_replacement_started`;
- `estimate_expertise_finding_replacement_resolved`.

В audit details сохраняются:

- `workflow_id`;
- `report_id`;
- `stage_key`;
- `finding_title`;
- `severity`;
- `normative_basis`;
- `xai_summary`;
- `comment`;
- `replacement_document_id`;
- `replacement_file_name`.

Это позволяет восстановить, кто принял решение, на каком выводе, на каком XAI-пояснении и с каким replacement-файлом.

## 18. Риски и ограничения

- `ПП РФ N 145` требует актуализации rules pack перед релизом.
- Нельзя утверждать юридическую подлинность печати или рукописной подписи: система проверяет наличие визуального признака и оформление, а не подлинность.
- На MVP можно проверять наличие визуального признака подписи/печати, а не подлинность или правовой статус реквизита.
- Орфографическая проверка должна учитывать OCR-noise, иначе будет много false positive.
- Названия файлов в реальных организациях часто хаотичны, поэтому stage 2 должен поддерживать user override.
- Комплектность по `ПП РФ N 145` зависит от типа объекта, стадии и сценария подачи; нужен profile selector.
