# Архитектурные решения

## 1. Назначение документа

Этот документ фиксирует ключевые архитектурные решения проекта:

- что выбрано в `MVP 1`
- почему выбрано именно это
- какие компромиссы приняты
- куда эти решения развиваются в `MVP 2+`

## 2. Web-first MVP

### Решение

Первый завершённый продуктовый контур строится как `web-first MVP`.

### Почему

- быстрее собрать сквозной сценарий
- проще работать с документами, таблицами и review
- меньше дублирования логики между платформами
- ценность проекта находится в core domain logic, а не в нативной оболочке

### Что дальше

- web остаётся базовым интерфейсом
- iOS относится к post-MVP/mobile branch

## 3. Monorepo

### Решение

Один репозиторий для `backend`, `frontend`, `infra`, `docs`, `samples`.

### Почему

- единый roadmap
- единый docs pack
- проще синхронизация между UI, API и benchmark artifacts
- удобнее для дипломного и инженерного сопровождения

## 4. Python backend: `FastAPI + SQLAlchemy + Alembic`

### Решение

- `FastAPI` как API-слой
- `SQLAlchemy 2` как ORM
- `Alembic` как миграционный контур

### Почему

- естественная интеграция с AI/data стеком
- высокая скорость разработки
- typed API
- управляемая доменная модель

## 5. `PostgreSQL + pgvector`

### Решение

Использовать одну БД и для транзакционных данных, и для vector search.

### Почему

- упрощает MVP
- снижает инфраструктурную сложность
- делает доменные связи и retrieval-контур прозрачными

### Как развивается дальше

- `MVP 2`: усиление retrieval и calibration
- `MVP 4`: усиление operational contour, если объёмы вырастут

## 6. Background jobs через `Celery + Redis`

### Решение

Обработка документов, анализ отчёта и generation вынесены в worker-контур.

### Почему

- долгие операции не должны блокировать HTTP
- нужны очереди, диагностика и повторный запуск
- это естественно для document/AI pipeline

## 7. Локальный AI runtime

### Решение

Использовать локальные embeddings и локальную LLM через `Ollama`.

### Почему

- автономность
- приватность документов
- воспроизводимый локальный стенд
- независимость от внешнего inference API

### Как развивается дальше

- `MVP 2`: более сильные embeddings / локальная LLM / более зрелая calibration-стратегия
- `Post-MVP`: fine-tuning и более зрелые multimodal stacks

## 8. Гибридный AI-контур

### Решение

Не использовать одну end-to-end LLM для всей регуляторной логики.

Текущая схема:

- обработка документов
- retrieval
- rule-based applicability / confidence / risk
- LLM-assisted generation
- сохранённый XAI

### Почему

- лучше контролируется
- лучше валидируется
- лучше объясняется пользователю
- устойчивее для auditable use case

## 9. XAI как сохранённый артефакт

### Решение

Объяснение хранится как сущность, а не как временный ответ модели.

### Почему

- позволяет аудит
- поддерживает экспорт
- поддерживает пересчёт после ручной правки
- делает reasoning trace частью бизнес-результата

## 10. Human-in-the-loop

### Решение

Система не утверждает результат без участия человека.

### Почему

- use case регуляторный
- часть требований требует интерпретации
- финальная ответственность остаётся у специалиста и approver

## 11. Базовый OCR-контур в `MVP 1`

### Решение

В `MVP 1` введён базовый OCR-контур на `Tesseract`.

### Почему

- даёт уже работающий image/PDF fallback
- закрывает базовые OCR-augmented benchmarks
- не требует сложного vision-contour на старте

### Что не закрывает

- layout-aware document understanding
- сложные mixed-layout и noisy scan pipelines
- multimodal reasoning

Эти задачи относятся к `MVP 2+`.

## 12. Базовый observability-контур в `MVP 1`

### Решение

Сразу включить runtime diagnostics, `Prometheus`, `Grafana`, `Alertmanager`.

### Почему

- background AI/document system без наблюдаемости плохо отлаживается
- для дипломного MVP уже полезно иметь измеримый runtime-контур

### Ограничение

Это базовый observability-контур, а не полный production platform contour.

## 13. Архитектурные переходы по roadmap

### `MVP 1 -> MVP 2`

- базовый OCR-контур -> более сильный OCR / vision-контур
- базовый локальный AI-контур -> более сильный стек локальных моделей
- текущий benchmark-слой -> более широкая валидация на `real_corpus`

### `MVP 2 -> MVP 3`

- аналитический инструмент -> workflow/integration platform
- single-scenario delivery -> multi-template workflow

### `MVP 3 -> MVP 4`

- pilot-ready product -> production/platform maturity

## 14. Итог

Архитектура `MVP 1` строилась как осознанный набор компромиссов:

- минимально достаточный продуктовый контур
- локальная воспроизводимость
- объяснимость
- управляемая сложность

Следующие версии усиливают уже существующий фундамент, а не отменяют его.
