# Roadmap направления «Государственная экспертиза» в EvidenceXAI

Дата актуализации: `2026-05-29`

## 1. Назначение документа

Этот документ описывает отдельный продуктовый трек EvidenceXAI для проектных организаций в РФ:

- пользователь: проектировочная компания;
- сценарий: подготовка комплекта проектной документации к государственной экспертизе;
- вход: документы с текстом, графикой, чертежами, подписями, основными надписями, сканами и приложениями;
- выход: проверочный отчет с ошибками, рекомендациями, XAI-объяснениями и интерактивными ссылками на источник замечания.

Трек разделен на `3` MVP. Финальный `MVP 3` описан как полный целевой контур без известных функциональных хвостов: все обсужденные проверки, vision/OCR, ГОСТ/СПДС-правила, интерактивные ссылки, XAI и экспорт должны быть реализованы внутри продукта. Будущие изменения законодательства и стандартов закрываются не ручной доработкой кода, а через нормативный registry и версионирование правил.

Отдельное прикладное ТЗ по сценарию `Отчет государственной экспертизы в части проверки достоверности определения сметной стоимости` вынесено в документ [state-expertise-estimate-cost-report-tz-roadmap.md](state-expertise-estimate-cost-report-tz-roadmap.md).

Актуальный фактический статус трека ведётся в [roadmap-status.md](roadmap-status.md). На `2026-05-29` уже реализован не только первоначальный skeleton: в backend есть спецworkflow для `ПП 145` и `ПП 87`, stages, findings, user decisions, replacement re-check, XAI, export, synthetic benchmark и реальный локальный прогон `Водоканалпроект / 1. ИРД / ПП 145`.

## 2. Цель направления

Сделать EvidenceXAI инструментом предварительной проверки проектной документации перед подачей в государственную экспертизу.

Система должна помогать проектной организации:

- быстрее найти орфографические и терминологические ошибки;
- проверить наличие подписей, реквизитов и основной надписи;
- проверить соответствие выбранным ГОСТ/СПДС/ЕСКД-правилам;
- проверить комплектность разделов проектной документации;
- увидеть каждое замечание в контексте исходного листа или фрагмента;
- понять, почему система сделала вывод;
- получить исправимый список замечаний до официальной подачи.

## 3. Нормативная рамка

Базовые источники для первого нормативного registry:

- `Постановление Правительства РФ N 87` — состав разделов проектной документации и требования к их содержанию: https://government.ru/docs/all/63014/
- `Постановление Правительства РФ от 05.03.2007 N 145` — порядок организации и проведения государственной экспертизы проектной документации и результатов инженерных изысканий, включая процедурную рамку приема документов, основания для отказа/оставления без рассмотрения и требования к комплекту, представляемому на экспертизу. Актуальную редакцию нужно сверять перед релизом rules pack: https://www.consultant.ru/document/cons_doc_LAW_66669/
- `ГОСТ Р 21.101-2026` — СПДС, основные требования к проектной и рабочей документации. По данным Росстандарта действует с `01.04.2026` и заменяет `ГОСТ Р 21.101-2020`: https://protect.gost.ru/gost/details/17bc12e8-6579-4145-b141-56855e772e7f
- `ГОСТ Р 21.001-2021` — СПДС, общие положения и классификация стандартов СПДС: https://protect.gost.ru/gost/details/88e90567-2700-420a-92fe-d23d8a7bb2ee
- `ГОСТ Р 2.105-2019` — общие требования к текстовым документам: https://protect.gost.ru/gost/details/0dd3cdfa-c15a-47b3-9e3b-4a90a43005c8
- `ГОСТ Р 2.104-2023` — основные надписи: https://protect.gost.ru/gost/details/69d422a2-3c0e-4561-a521-0c99f9cf4417
- `ГОСТ 2.301-68` — форматы листов: https://protect.gost.ru/gost/details/aa681f87-ff49-4115-ad25-169e15d2af06
- `ГОСТ 2.304-81` — чертежные шрифты: https://protect.gost.ru/gost/details/2acb3258-c28c-4e4a-b7ac-208043f2d95e
- `ГОСТ Р 2.316-2023` — надписи, технические требования и таблицы в графических документах: https://protect.gost.ru/document.aspx?control=7&id=256227
- `ГОСТ 21.501-2018` — правила выполнения рабочей документации архитектурных и конструктивных решений: https://protect.gost.ru/gost/details/a241e289-aac3-4ee2-ad44-3259f9774799
- `ГОСТ 21.508-2020` — правила выполнения рабочей документации генеральных планов: https://protect.gost.ru/document.aspx?control=7&id=238277
- `ГОСТ 21.602-2016` — правила выполнения рабочей документации отопления, вентиляции и кондиционирования: https://protect.gost.ru/default.aspx/document.aspx?control=7&id=205649
- `ГОСТ 21.704-2011` — правила выполнения рабочей документации наружных сетей водоснабжения и канализации: https://protect.gost.ru/document.aspx?DocOnPageCount=15&RegNum=1&baseC=6&control=7&id=180553&month=11&page=6&search=&year=-1

Важное ограничение: полные тексты стандартов могут иметь лицензионные ограничения. В продукте нужно хранить не пиратские копии стандартов, а rule registry: идентификатор правила, краткую проверяемую формулировку, ссылку на источник, версию и дату актуализации.

## 4. Пользовательский путь

1. Пользователь входит в EvidenceXAI.
2. Создает организацию типа `Проектная организация`.
3. Заполняет профиль организации:
   - название;
   - ИНН, КПП, ОГРН;
   - адрес;
   - сайт, email, телефон;
   - ГИП;
   - ответственный за комплект;
   - сведения о допуске/СРО, если они нужны в сценарии.
4. Создает отчет типа `Государственная экспертиза`.
5. Выбирает профиль проверки:
   - стадия: `ПД`, `РД`, либо смешанный комплект;
   - объект: здание, реконструкция, линейный объект, инженерные сети, благоустройство;
   - разделы по `ПП РФ N 87`;
   - комплектность подачи по `ПП РФ N 145`;
   - применимые СПДС/ЕСКД/ГОСТ-профили.
6. Загружает комплект:
   - PDF с текстовым слоем;
   - сканы PDF;
   - JPG/PNG/TIFF листы;
   - DOCX пояснительных записок;
   - XLSX/CSV ведомостей;
   - IFC/DWG/архивы как целевой формат финального MVP.
7. Запускает обработку.
8. Система извлекает текст, графику, подписи, штампы, таблицы, основную надпись и координаты.
9. Пользователь запускает анализ.
10. Система формирует замечания:
    - орфография;
    - терминология;
    - подписи;
    - основная надпись;
    - состав комплекта;
    - ГОСТ/СПДС/ЕСКД-несоответствия;
    - слабые или спорные места.
11. Пользователь открывает интерактивный viewer и видит замечание на конкретной странице/листе.
12. Пользователь смотрит XAI-объяснение:
    - какое правило применено;
    - какой фрагмент найден;
    - какие признаки совпали;
    - чего не хватает;
    - почему уровень риска именно такой.
13. Пользователь подтверждает, отклоняет или переводит замечание в доработку.
14. После исправлений загружает новую версию комплекта.
15. EvidenceXAI сравнивает версии и показывает, какие замечания закрыты.
16. Пользователь экспортирует:
    - итоговый отчет замечаний `DOCX`;
    - матрицу `XLSX`;
    - аннотированный `PDF/HTML`;
    - XAI-пакет;
    - ZIP доказательной базы.

## 5. Целевой выходной результат

На выходе пользователь должен получить:

- реестр замечаний;
- список орфографических ошибок;
- список терминологических и стилистических замечаний;
- список листов без подписи или с неполной основной надписью;
- список нарушений правил оформления;
- список несоответствий составу разделов;
- список отсутствующих документов и процедурных реквизитов комплекта по `ПП РФ N 145`;
- список замечаний по чертежам, таблицам, штампам и графическим элементам;
- рекомендации по исправлению;
- нормативное основание по каждому замечанию: ГОСТ, СПДС, ЕСКД, СП, постановление, словарное правило или внутреннее правило EvidenceXAI;
- пункт, раздел, таблицу или приложение нормативного документа, если правило можно привязать к конкретному месту;
- версию нормативного документа и дату актуализации правила;
- ссылку на официальный или справочный источник нормативного документа, если она доступна;
- интерактивные ссылки на страницу, область и фрагмент;
- XAI-объяснение по каждому замечанию;
- приоритет исправлений;
- повторную проверку после загрузки исправленной версии;
- экспортный пакет для внутреннего контроля перед подачей в экспертизу.

## 6. Архитектурный принцип

Новый трек не должен быть отдельной системой. Он расширяет текущий EvidenceXAI:

- существующая организация остается multi-tenant scope;
- документы остаются в общем document pipeline;
- требования и замечания используют общий registry;
- XAI хранится в текущей модели explanations, но расширяется новыми типами evidence;
- отчеты, версии, риски, уведомления и аудит переиспользуются;
- новые проверки добавляются через domain-specific rule packs.

## 8. XAI-метод для государственной экспертизы

XAI должен работать на уровне каждого замечания, а не только на уровне итогового отчета.

Минимальный XAI payload:

- `conclusion`: что обнаружено;
- `finding_type`: орфография, подпись, ГОСТ, комплектность, графика;
- `rule_ref`: код правила;
- `rule_source`: стандарт, пункт, версия;
- `normative_basis`: человекочитаемое основание вывода, например `ГОСТ Р 21.101-2026, раздел 5`;
- `normative_url`: ссылка на карточку стандарта, постановления или другой официальный/справочный источник;
- `normative_quote_policy`: ссылка на пункт без хранения полного текста стандарта, если полный текст ограничен лицензией;
- `applicability_reason`: почему правило применимо к этому листу/разделу;
- `evidence`: фрагменты текста, координаты, OCR-блоки, визуальные признаки;
- `logic_chain`: цепочка вывода;
- `confidence`: уверенность;
- `risk_level`: уровень риска для подачи в экспертизу;
- `recommended_action`: что исправить;
- `interactive_anchor`: ссылка на страницу, bbox и подсветку;
- `alternatives`: почему соседние фрагменты/листы не выбраны как evidence;
- `human_review_trace`: кто подтвердил/отклонил замечание.

Виды XAI:

- `Rule XAI`: объяснение примененного ГОСТ/СПДС/ЕСКД-правила.
- `Evidence XAI`: почему выбран конкретный фрагмент или область листа.
- `Layout XAI`: почему область классифицирована как основная надпись, подпись, таблица, примечание, чертежная зона.
- `Completeness XAI`: почему документ считается присутствующим, отсутствующим или неполным по требованиям подачи на экспертизу.
- `Gap XAI`: чего не хватает до соответствия.
- `Revision XAI`: почему замечание считается закрытым или не закрытым после повторной загрузки.

Каждый XAI-блок в UI и export должен отвечать на вопрос: `согласно какому нормативному основанию сделан вывод`. Если замечание не связано с ГОСТ/СПДС/ЕСКД напрямую, система должна явно показывать тип основания:

- `Орфография`: словарь, LanguageTool-правило, пользовательский словарь или корпоративный словарь терминов;
- `Комплектность`: `ПП РФ N 87` или выбранный профиль комплекта;
- `Комплектность подачи`: `ПП РФ N 145`, профиль стадии, тип объекта и перечень ожидаемых документов для передачи на государственную экспертизу;
- `Оформление листа`: ГОСТ/СПДС/ЕСКД rule pack;
- `Подпись`: rule pack основной надписи, профиль роли или metadata PDF-подписи;
- `Системное предупреждение`: внутреннее правило EvidenceXAI с кодом и описанием.

## 9. Модели и алгоритмы

### 9.1. OCR и текст

- PDF text extraction для документов с текстовым слоем.
- OCR для сканов и изображений.
- Текущий локальный OCR: `Tesseract` внутри backend/worker runtime.
- Возможный будущий OCR: локальный `PaddleOCR`, `ONNX` или аналогичный provider с поддержкой русского языка и координат, установленный на нашем сервере. Это не внешний OCR-сервис.
- Fallback: текущий `Tesseract`.
- Нормализация текста:
  - удаление OCR-шумов;
  - восстановление переносов;
  - нормализация пробелов;
  - сохранение координат.

### 9.2. Орфография и терминология

- локальный `LanguageTool` или аналогичный grammar/spell engine;
- специализированный словарь проектной документации;
- white-list терминов, сокращений, марок разделов, шифров листов;
- fuzzy matching для OCR-ошибок;
- XAI по каждому исправлению: исходное слово, предложенная замена, причина, источник словаря.

### 9.3. Layout и графика

- page segmentation;
- определение текстовых блоков;
- определение таблиц;
- определение основной надписи;
- определение подписных зон;
- определение штампов и реквизитов;
- определение выносок и технических требований.

Целевой стек:

- `LayoutLMv3` / `DocFormer` / `DiT`-подобный document layout model;
- `YOLO/RT-DETR`-подобный detector для областей листа;
- rule-based postprocessing по геометрии листа;
- отдельный classifier для основной надписи и подписей.

### 9.4. Подписи

Проверки:

- наличие подписных полей;
- заполненность ролей;
- наличие графической подписи;
- наличие даты;
- наличие фамилии/инициалов;
- наличие электронной подписи, если документ подписан как PDF-контейнер;
- соответствие подписей требуемому профилю листа.

Важно: система не должна утверждать подлинность рукописной подписи. Она должна определять наличие/отсутствие визуального признака подписи и полноту реквизитов.

### 9.5. ГОСТ/СПДС/ЕСКД rules engine

Rules engine должен поддерживать:

- применимость правила к стадии и типу документа;
- версию стандарта;
- severity;
- machine-checkable condition;
- evidence query;
- validation function;
- XAI-template;
- human override.

Типы проверок:

- формат листа;
- основная надпись;
- подписи и реквизиты;
- наличие обязательных разделов;
- соответствие состава разделов;
- оформление текстовых документов;
- оформление графических документов;
- наличие технических требований и таблиц;
- терминология;
- ссылки на нормативные документы;
- consistency между листами, ведомостями и пояснительной запиской.

### 9.6. Retrieval и LLM

LLM не должна быть единственным судьей соответствия ГОСТ.

Роль LLM:

- нормализовать замечания;
- суммаризировать причины;
- помогать извлекать слабоструктурированные реквизиты;
- генерировать рекомендации;
- объяснять вывод понятным языком.

Роль deterministic/rule layer:

- применять проверяемые правила;
- считать confidence;
- формировать severity;
- фиксировать evidence;
- сохранять audit trace.

## 10. MVP 1 — «Базовая экспертиза комплекта»

### Цель

Добавить в EvidenceXAI новый сценарий, который уже полезен проектной организации: загрузить комплект, извлечь текст/листы, найти базовые замечания и получить XAI-отчет.

### Функции

- новый тип организации: `project_company`;
- новый тип отчета: `state_expertise`;
- профиль проекта:
  - стадия `ПД/РД`;
  - тип объекта;
  - список разделов;
  - выбранный нормативный профиль;
- загрузка `PDF`, `DOCX`, `XLSX`, `CSV`, `TXT`, `JSON`, `JPG`, `PNG`, `TIFF`;
- OCR для изображений и image-only PDF;
- извлечение текстового слоя из PDF;
- разбиение на страницы и блоки;
- сохранение координат OCR-фрагментов;
- базовая орфография через локальный checker;
- rule pack:
  - наличие текстового слоя/OCR;
  - наличие основной надписи по эвристикам;
  - наличие подписных маркеров;
  - базовая комплектность разделов по выбранному профилю;
  - базовая комплектность подачи по `ПП РФ N 145`;

## 11. MVP 2 — «Layout-aware экспертиза и сильный XAI»

Перейти от текстово-эвристической проверки к layout-aware анализу проектных листов.

  - дата;
  - фамилия/инициалы;
- rule pack `ГОСТ Р 21.101-2026`;
- rule pack `ГОСТ Р 2.105-2019`;
- rule pack `ГОСТ Р 2.104-2023`;
- rule pack `ГОСТ 2.301-68`;
- rule pack `ГОСТ 2.304-81`;
- rule pack `ГОСТ Р 2.316-2023`;
- section completeness по `ПП РФ N 87`;

- glossary/terminology engine;

- alternative evidence;
- confidence decomposition;
- missing evidence explanation;
- human review trace;

### UI

  - снизу XAI;

### Ограничения MVP 2

- электронная подпись может проверяться на уровне PDF metadata/signature presence, без полноценного юридического validation chain.

## 12. MVP 3 — «Полный контур подготовки к государственной экспертизе»

## 15. Риски реализации

- качество OCR на плохих сканах;
- вариативность оформления проектных листов;
- юридическая чувствительность формулировок по ГОСТ;
- невозможность хранить полные тексты стандартов без лицензий;
- ложноположительные замечания по подписям;
- сложность DWG/DXF/IFC без внешних конвертеров;
- необходимость benchmark-разметки;
- высокая вычислительная стоимость vision-моделей.

Митигировать через:

- staged rollout;
- human review;
- confidence thresholds;
- rule versioning;
- benchmark corpus;
- clear XAI;
- marking advisory nature of the check.

## 16. Оставшиеся уточняющие вопросы

Перед началом реализации нужно зафиксировать:

1. Первый demo-объект: здание, реконструкция, линейный объект, инженерные сети или благоустройство?
2. Первая стадия: `ПД`, `РД` или обе сразу?
3. Нужна ли нативная поддержка `DWG/DXF` в первом MVP, или до `MVP 3` принимаем только PDF/exported drawings?
4. Орфографию делаем только локально или допускаем внешний сервис?
5. Подписи проверяем только как визуальное наличие, или сразу добавляем проверку электронных подписей PDF?
6. Есть ли у нас обезличенный реальный комплект проектной документации для benchmark, или начинаем с синтетического корпуса?
7. Нужна ли в первом релизе юридическая формулировка “предварительная автоматизированная проверка, не заменяет государственную экспертизу” в UI и exports?

## 17. Рекомендуемый порядок старта
